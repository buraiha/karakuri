## 1 目的と文書の位置づけ

Karakuriは、日常の小さな不便を解消する機能をまとめたWebアプリとする。最初の機能として、iPhoneで音声入力した文章を別のPC端末へ送り、ブラウザで受信してコピーできるようにする。AIを使って小さく作り、実際の利用で価値を確かめる。

本書は現在有効な製品要件の正本とする。今回ユーザーが指定したPRDを反映し、元資料のPersonalToolsという名称は、現在のプロジェクト名Karakuriへ統一した。最初の機能名VoiceRelayは仮称で、正式名称は未決。

- 第2節はPRDで「確定要件」とされた要求と、その後ユーザーが明示した追加・確認事項を確定要件として扱う。
- 第3節の設計前提、第4節の具体化、第5節の提案およびそれらから派生する受け入れ条件は、第2節で確定した内容を除き、実装前の確認対象とする。PRDの提示だけで、補足・提案まで一括して合意済みとは扱わない。
- 本書の反映は文書更新であり、アプリ実装、環境変更、コミット・push・デプロイの開始指示ではない。
- 作業手順は [AGENTS.md](../AGENTS.md)、要件整理は [要件定義ガイド](../.ai/guides/01-requirements.md) に従う。

## 2 確定要件

### 2.1 利用体験

1. iPhone を文章入力の起点とし、音声入力を活用する。
2. 利用者はひとまとまりの文章を作成し、内容を確認して送信ボタンを押す。
3. 別の PC などで開いている受信画面に、送信した文章を即時に反映する。利用者によるページ再読み込みは不要とする。
4. 受信側では文章をコピーし、必要なアプリへ貼り付けて利用する。
5. この文章連携を、Karakuri に含まれる複数機能のうち最初の一つとして提供する。

**リアルタイムの対象は、送信を確定した文章である。入力途中の文字列や音声を逐次共有する機能ではない。**

### 2.2 認証と利用許可

1. Karakuriおよび各アプリの機能を利用するには、Googleアカウントによる認証を必須とする。未認証では機能を利用できない。
2. 利用希望者が登録すると、利用申請が管理者に届く。
3. 管理者は管理画面で申請を確認し、承認または拒否を判断する。
4. Google 認証の成功とアプリ利用の承認を別に扱う。認証済みであっても承認待ちの利用者はツールを利用できない。

### 2.2.1 ログインセッションの有効期間

- Google認証によるログイン成立時から14日間（336時間）を固定の有効期間とする。
- 利用・通信・セッション内容の更新によって有効期限を延長しない。ブラウザを閉じても、有効期間内はログイン状態を維持する。
- 期限に達したセッションでは機能を利用できず、再びGoogle認証を経てログインする。再ログイン成立時から新たな14日間を開始する。
- ログアウト時は対象セッションを無効化する。
- セッションの有効期間と利用承認・アプリ権限を分離する。有効なセッションがあっても、アクセス時に必要な承認・権限を満たさなければ利用できない。

### 2.3 アプリごとの利用権限とデータ管理

1. Karakuri内の各ツールを、本節では「アプリ」と呼ぶ。管理者は、利用者ごとに各アプリの利用を許可・取り消しできる。
2. Google認証、Karakuri全体の利用承認、個別アプリの利用権限を区別する。各アプリを利用できるのは、認証済み・全体の利用承認済み・対象アプリの利用権限あり、のすべてを満たす利用者とする。
3. 利用者、アプリ、利用者とアプリの利用権限の対応をデータベースで永続管理し、「誰がどのアプリを使えるか／使えないか」を判定できるようにする。利用許可を確認できないアプリは利用できない。
4. 管理者は管理画面で利用者ごとのアプリ利用可否を確認・変更できる。一般利用者は自身の権限を変更できない。
5. 利用権限は画面表示だけでなく、サーバー側の機能・API・リアルタイム接続にも適用する。文章連携アプリでは送信・取得・受信を保護する。
6. 管理者はユーザー・アプリの組み合わせごとに「課金した／しない」を管理し、その状態に応じて対象アプリを「利用できる／できない」に切り替えられる。課金状態と対応する利用可否をデータベースに保存し、他のユーザー・アプリには影響させない。一般利用者は自身の課金状態を変更できない。
7. 今回確定するのは、管理者による課金状態の管理と利用可否への反映である。料金、契約、請求・入金のどの時点を「課金した」とするか、有効期間、無料利用・免除の扱い、および決済サービスによる自動処理は未決とする。

### 2.4 基本の画面遷移

- 通常の利用経路は「ログイン画面 → アプリ選択画面 → 選択したアプリの機能画面」とする。
- ログイン後、全体の利用承認が未完了の場合は利用申請・承認待ちの案内へ進む。拒否された場合は利用不可の状態を案内する。
- 承認済みの利用者はアプリ選択画面から、利用可能なアプリの機能画面へ進む。機能画面への直接アクセスにも認証・承認・アプリ利用権限の検証を適用する。
- 権限のないアプリを選択画面に表示するかは未決とする。

## 3 設計前提

以下は構想を実用化するための前提とする。ユーザーが明示した技術仕様ではないため、実装開始時に確認する。

- iPhone と PC のブラウザで使う Web アプリとし、業務用 Windows PC には専用ソフトや拡張機能をインストールしない。
- 文章の連携は、同じ利用者がログインした端末間に限定する。他の利用者の文章は閲覧・受信・変更できない。
- 管理者は利用申請・アプリの使用許諾・ユーザーとアプリごとの課金状態および利用可否を管理する役割であり、他の利用者の文章を閲覧する権限を当然には持たない。
- 入力と受信は別端末で利用できる画面として用意する。専用の端末登録やペアリングは MVP では必須としない。
- 管理画面の申請一覧を「申請が届く」最小構成とする。メールなどの外部通知は別途判断する。
- 業務情報を外部サービスへ送信してよいかは所属先のルールに従う。許可が確認できるまでは、機密情報を含まないテスト文章で試す。

## 4 MVP の機能

### 4.1 ホームと共通導線

- 第2.4節に従い、ログイン後のアプリ選択画面をKarakuriのホームとし、ツール一覧から各アプリの機能画面へ進む。
- 最初は文章連携機能のみを掲載し、後から別のツールを追加できる構成にする。各アプリの利用可否は第2.3節の権限に従う。権限のないアプリを一覧に表示するかは未決。
- ログイン、ログアウト、利用申請状況への導線を設ける。

### 4.2 入力画面

- iPhone で使いやすい文章入力欄と送信ボタンを設ける。
- 送信前に文章を手動で修正できるようにする。
- 送信操作前の文章は受信側へ配信しない。
- 空の文章は送信できないようにする。
- 送信中、送信成功、送信失敗を区別して表示する。
- 失敗時に未送信の文章を消さず、再送できるようにする。
- 連打や再送による意図しない重複を防ぐ方針を設ける。

### 4.3 受信画面

- 送信済み文章を、開いたままの受信画面に自動反映する。
- 文章を選択してコピーできるようにする。コピー操作用ボタンの設置を推奨する。
- 接続中、切断中、再接続中など、受信できる状態か判断できる表示を設ける。
- 再接続時に取りこぼしを確認・回復する方針を設ける。保持対象と期間は第 8 節で決める。

### 4.4 利用申請と管理画面

- 申請者を Google アカウントにひもづけて管理する。
- 最低限の状態を `pending`（承認待ち）、`approved`（承認済み）、`rejected`（拒否）とする。
- 一般利用者は自身の状態を確認できるが、状態を自分で承認済みに変更できない。
- 管理者は申請者と状態を確認し、承認・拒否を実行できる。
- `pending` と `rejected` は文章の送受信ができない。
- 管理画面と管理操作は管理者だけが利用できる。
- 第2.3節に従い、管理者が利用者ごとの各アプリの利用権限を確認・付与・取り消しできる。全体の利用承認だけで全アプリを利用可能にはしない。
- 管理者はユーザー・アプリごとの課金状態を管理し、その状態に応じて対象アプリの利用可否を切り替えられる。

## 5 実装方式の提案

以下は確定事項ではない。必要最小限の構成を選び、採用理由を記録する。

- 音声入力は、まず iPhone 標準のキーボード音声入力を利用する。独自の音声認識 API、音声ファイルのアップロード・保存、ネイティブアプリ開発は初期構成では不要とする案を優先する。
- リアルタイム反映は WebSocket または Server-Sent Events などを候補とする。利用環境とホスティング制約を踏まえて決定する。
- 最初の表示は「最新の送信文章を表示する」構成を候補とする。履歴一覧や複数文章の保持が必要かは実装前に確認する。
- データは利用者、申請状態、管理者権限、アプリ、利用者ごとのアプリ利用権限と課金状態、送信文章とその所有者・送信時刻を最小の概念として扱う。第2.3節のデータベースによる権限管理は確定要件とし、具体的な製品・スキーマは技術選定後に決める。

### 5.1 最低限の安全設計の提案

- 本番では HTTPS を使う。
- 認証状態、承認状態、所有者、管理者権限はサーバー側でも検証する。画面上のボタン非表示だけで保護しない。
- リアルタイム接続にも認証と利用者ごとのアクセス制御を適用する。
- URL を知っているだけで文章を読める公開共有方式は採用しない。
- 秘密鍵や認証用シークレットをブラウザ配布コード、公開リポジトリ、ログに含めない。
- 文章は実行可能な HTML として扱わず、安全にテキスト表示する。
- 本文を不要にログへ出さない。入力サイズ制限と過剰な送信への対策を設ける。

## 6 受入基準

MVP は、次の操作を実機または対象ブラウザで確認できることを完了条件とする。設計前提と提案から派生する項目は、実装開始時に合意する。

| ID | 確認内容 | 合格条件 |
| --- | --- | --- |
| A01 | iPhone で入力する | 音声入力した日本語を編集し、送信できる |
| A02 | 送信前の文章を確認する | 別端末には入力途中の文章が表示されない |
| A03 | 別端末で受信する | 同一利用者で開いた PC の画面に、送信確定後、再読み込みなしで文章が表示される |
| A04 | 文章を使う | 日本語と改行を含む受信文章をコピーし、別アプリへ貼り付けられる |
| A05 | 新規利用申請を行う | 管理画面に承認待ちの申請が表示される |
| A06 | 承認・拒否する | 管理者の判断が反映され、承認済みだけが文章を送受信できる |
| A07 | 権限を確認する | 未ログイン、承認待ち、拒否済み、一般利用者からの不正な直接アクセスも拒否される |
| A08 | 利用者を分離する | 利用者 A の文章を利用者 B が取得・受信・変更できない |
| A09 | 通信失敗から戻る | 失敗を表示し、入力を保持して再送できる。受信側は切断状態を把握できる |
| A10 | Windows PC で使う | 専用ソフトや拡張機能を追加せず、対象ブラウザで受信とコピーができる |
| A11 | アプリ別の利用権限を管理する | 全体承認済みでもアプリ権限のない利用者は対象機能・API・受信接続を利用できない。管理者が付与すると利用可能になり、取り消すと利用不可になる。他アプリの権限は変わらず、一般利用者は自己付与できない |
| A12 | 権限を永続管理する | 利用者・アプリ・権限の対応がデータベースに保存され、再ログイン後も利用可否へ反映される |
| A13 | 課金状態と利用可否を管理する | 管理者がユーザー・アプリごとの課金状態を変更し、対象アプリの利用可否へ反映できる。状態はDBに保存され、他の組み合わせに影響せず、一般利用者は変更できない |
| A14 | 基本の利用経路を確認する | 承認済みの利用者がログインからアプリ選択を経て利用可能な機能画面へ進める。承認待ち・拒否・アプリ権限なしの場合は機能を利用できない |

「即時」の許容時間は未定。合意した通信環境で、送信確定から表示までの時間を計測し、具体的な目標値を設定する。

## 7 MVP のスコープ外

- 入力途中のライブ共有、音声・動画の配信。
- 複数利用者間のチャット、他人への共有、共同編集。
- ネイティブアプリ、PC 常駐ソフト、ブラウザ拡張機能。
- 他アプリへの自動貼り付け、OS 全体のクリップボード同期。
- AI による要約・校正・翻訳などの追加加工。
- 決済サービス連携・自動請求・自動入金確認の実装（管理者による課金状態と利用可否の管理は第2.3節の対象に含む）、一般公開向けの大規模運用、最初から多数のツールを実装すること。

## 8 実装前に決める事項

以下は要件整理時の判断事項一覧。後掲の「決定済み事項の補足」で確定した内容は未決から除き、具体的な実装設計は関連設計書で管理する。

1. **データ管理**：最新一件か履歴一覧か、保存期間、削除方法、端末再接続時の復元範囲、ログの内容と保持期間。
2. **アカウント管理**：最初の管理者の設定方法、個人 Google アカウントと Google Workspace の許容範囲、拒否後の再申請、承認取消や利用停止の要否。
3. **送信仕様**：送信後の編集・取消・履歴、最大文字数、連続送信や重複の扱い、受信画面が閉じている間の扱い。
4. **通知と表示**：申請通知の方法、最新文章の置換か追記か、送信成功がサーバー受付と受信端末到達のどちらを意味するか。
5. **利用環境**：対象の iPhone と PC ブラウザ、業務用ネットワークからの接続可否、許容する遅延の数値。
6. **技術と運用**：言語、フレームワーク、Google 認証の具体的な実装方式、ホスティング、データストア、リアルタイム通信方式、運用費用。
7. **アプリ権限の運用と将来課金**：初回承認時の権限付与方法、権限取消の既存接続への反映タイミング、権限のないアプリの一覧表示、変更履歴の保持。料金・契約・決済方式、「課金した」の判定時点、有効期間、無料利用・免除の扱い。管理者による課金状態と利用可否の管理自体は確定。
8. **名称**：文章連携機能の正式名称。名称の商標・サービス名の重複確認は未実施。

### 決定済み事項の補足（2026-10-30）

- 言語・フレームワークはPython＋Djangoに決定した。具体的な実装構成は [基本構成設計](design.md) を参照する。
- 課金状態と利用許可は別項目として管理し、管理者が同じ画面で明示して保存する。無料での利用許可を可能とし、課金状態だけで権限を自動付与しない。
- ログインセッションは第2.2.1節の14日固定とする。
- DBはSQLiteで初期運用し、設定でPostgreSQL・MySQLへ切り替えられる構成とする。接続先変更とデータ移行は別の操作として扱う。

未決事項を AI が確定要件として補完しないこと。実装時に必要な判断を提示し、採用した前提と未解決事項を記録する。

## 9 検証方針

実装が依頼された段階で、Google 認証と承認制を備えた上で、「iPhone で入力して送信 → 同じ利用者の PC ブラウザに表示 → コピー」の一連の体験を作る。非機密の文章で受入基準を確認し、日常で手間が減るかを試す。その結果を見て、履歴や別ツールなどの追加を判断する。

| 入力端末 | iPhone。音声入力した文章を確認して送信 | 確定要件。機種・iOS・ブラウザの対象バージョンは未決、未検証 |
| 受信端末 | 別のPC等のブラウザ | 確定要件。OS・ブラウザ・バージョンの対応範囲は未決、未検証 |
| Windows PC | 専用ソフト・拡張機能を追加しない利用 | 第3節の設計前提。業務用ネットワークからの接続可否も未検証 |
| 接続先 | Webアプリのホスティング先・データストア | DBはSQLiteで初期運用しPostgreSQL・MySQL切り替えに対応。ホスティング先は未決。PC自体を接続先サーバーとする要件ではない |
| 外部サービス | Googleアカウント認証 | 確定要件。アカウント種別・実装方式は未決、未検証 |

## 11 要件IDと検証の対応

以下のIDは一意で安定した識別子とし、削除後に別の意味で再利用しない。
「要確認」はPRDの設計前提・具体化に由来する項目であり、「提案」は実装方式の候補とする。実装・検証の個別結果はtask0004と開発ガイドに記録する。自動テストの合格をMVP全体や実Google認証・実機試験の合格とは扱わない。
第6節のA01〜A10は既存の受入基準IDとして保持し、追加したA11〜A14とともに、製品要件IDとは分ける。

### 11.1 機能要件
